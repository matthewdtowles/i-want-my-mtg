# 7.3 Import Inventory by Picture - Plan

Plan for [#301](https://github.com/matthewdtowles/i-want-my-mtg/issues/301). Written 2026-08-09.

Goal: a user points a camera at a card (or a photo of several cards), the app works out
which printings those are, shows them for confirmation, and writes them to inventory.

---

## 1. Where this work lives

**No new repo.** The feature splits cleanly across the three repos that already exist,
and each piece lands in the repo that already owns that concern.

| Repo | Owns |
|---|---|
| **i-want-my-mtg** (this repo) | The scan API, the match logic, the review/confirm step, the inventory write, the premium gate, the web UI, and the migration for any new table. |
| **scry** | Building the reference fingerprint index: downloading each printing's art, computing its hash, writing it to the DB. This is a bulk pass over every card, run on a schedule, which is exactly what scry is. |
| **i-want-my-mtg-mobile** | Camera capture, framing guide, upload, and the review screen. Later: on-device matching against a downloaded index. |

**Why not a separate recognition service.** The only argument for one is heavy image
dependencies (OpenCV and friends) that we do not want inside the NestJS container. The
plan below is arranged so the server never needs them: the hard perception either runs
in a model API (Stage 1) or reduces to a Hamming-distance scan over a small in-memory
array (Stage 2), which is ~40 lines of TypeScript with no native modules. If Stage 2's
card-edge detection later has to move server-side, that is the one trigger for a small
sidecar, and it should be a scry subcommand before it is a new repo - scry is already
Rust, already has `image`-ecosystem crates available, and already runs as a binary on the
box.

**Why the index build belongs in scry, not web.** It is a 100k-row bulk pass with
external HTTP fetches and rate limiting, incremental on new sets, run from cron. Every
one of those traits describes existing scry commands and none of them describes the web
app. Web owns the schema (migration creates the table), scry fills it. This is the same
split as `price` / `set_price` and follows the existing deploy-order rule: publish scry
first, deploy web second.

## 2. What "identify a card" actually means here

Three different signals can identify a printing, and they are not equally good:

1. **Collector-number line** (bottom-left on cards from 2015 on): `0123/281 M21 EN`.
   This is set code plus number, which is an *exact* printing match through the existing
   `CardImportResolver` (`findBySetCodeAndNumber`). Best possible outcome. Roughly the
   last decade of cards have it.
2. **Card name** (title bar). Identifies the *card* but not the *printing*. Lightning
   Bolt has 20+ printings at different prices. Needs a printing choice: default to the
   cheapest or most recent, and let the review step change it.
3. **Art fingerprint** (perceptual hash of the art box). Identifies the *artwork*, which
   usually narrows to one printing but collapses across reprints that reuse art. Works on
   old cards with no collector number, works on non-English cards, works when the name is
   glare-blown.

The right system uses all three: the collector line when it is readable, the art hash as
the backbone, and the name as a cross-check. The staging below adds them in the order of
value-per-unit-of-work, not in that order.

### Things that will go wrong, listed once

- **Reprints share art.** The hash returns a set of printings, not one. This is not a bug
  to fix, it is a disambiguation step the UI must have. Same art plus a readable collector
  line resolves it; same art with no collector line is a user pick.
- **Foils.** Glare wrecks both OCR and hashing. Foil is also a real inventory axis
  (`inventory.is_foil`), so it cannot be guessed away. Treat it as a review-step toggle,
  defaulted from whether the printing even has a foil version (`card.hasFoil`).
- **Double-faced, full-art, borderless, showcase frames.** The art box is at a different
  place, so a fixed art-crop rectangle mis-crops them. Handle by hashing the *whole warped
  card* as a second fingerprint alongside the art crop, and matching against both.
- **Sleeves, angle, phone-camera color cast.** Perspective correction handles angle;
  hashing on a downscaled grayscale image handles color cast; sleeves mostly just add a
  border, which the card-edge detection must not mistake for the card edge.
- **Condition.** Asked about in the issue comment. **Out of scope, and nothing to do**:
  the `inventory` table has no condition column at all (`cardId`, `userId`, `isFoil`,
  `quantity`). Pricing does not vary by condition anywhere in this app today. If condition
  is ever modeled, it is its own roadmap item and it is a user input, not something to
  read off a photo.

## 3. Staged plan

### Stage 0 - Decide the accuracy bar and the quota (before writing code)

Two numbers drive every later choice:

- **Target:** what fraction of single-card photos must resolve to the correct printing
  with no user correction? Suggest 90% for "in-frame, decent light, 2015-or-newer card"
  and treat anything below that as "show candidates, do not auto-fill".
- **Quota:** scans per month for a Premium user. Needed because Stage 1 has a real
  per-scan cost. Suggest 500/month, which is generous for a collector and cheap at
  Stage 1 prices, and stops the pathological case of someone scripting the endpoint.

Also decide up front: **scanning is Premium-gated** (the Appendix already promises it as a
Premium pitch), and it uses the existing `SubscriptionGuard` plus `@RequiresSubscription()`.
Its refusal message is already neutral ("Active subscription required."), which satisfies
the standing 3.1.1 rule, so no new wording risk. The quota-exceeded message must be written
to the same rule: no "Premium", no tier name, no pricing URL, since the mobile app reaches
this endpoint.

### Stage 1 - Ship it with a vision model (2 to 3 weeks)

The fastest path to a feature people can use. The model does the perception; we do the
resolution against our own catalog.

**Flow.** Client uploads a photo to `POST /api/v1/inventory/scan` (multipart, reuse the
existing upload interceptor pattern from `csv-upload.interceptor.ts`, new size limit and
`image/jpeg|png|webp` allow-list). Server downscales the image, sends it to a vision model
with a strict output shape: for each card visible, return `name`, `setCode`, `number`,
`quantity`, `isFoil`, and a confidence. Server then runs every returned row through the
**existing `CardImportResolver`**, which already tries id, then set+number, then name+set,
and already returns per-row errors. Result is a list of candidates plus unresolved rows.

**Why this is cheap to build:** the entire back half already exists. `CardImportResolver`
and `InventoryImportService.importCards` are exactly the "rows in, inventory out, per-row
errors" pipeline that CSV import uses. Scanning becomes a third parser feeding the same
path, next to the Moxfield/Deckbox/TCGPlayer parsers.

**What it buys:** multi-card photos and binder pages work on day one, which the hash
approach does not give cheaply. Angles, lighting, and partial occlusion are handled by the
model. Old cards with no collector number still work, because the model reads the name.

**What it costs:** a few cents per scan at most, a couple of seconds of latency, an
external dependency on the request path, and a real hallucination risk on obscure cards -
which is exactly why every row goes through `CardImportResolver` against our own catalog
and anything that does not resolve is shown as unresolved rather than guessed.

**Deliverables**
- Migration: `scan_usage` (or a counter on the user) for the monthly quota. One table, one
  upsert per scan.
- `src/core/inventory/scan/` - scan service, model client behind a port so it can be
  swapped or mocked in tests.
- `POST /api/v1/inventory/scan` returning candidates; **no write**. The write goes through
  the existing inventory endpoints after the user confirms. Keeping identify and write
  separate is what makes the review step honest and makes the endpoint safe to retry.
- Web UI: an upload/camera page plus a review table (thumbnail, name, set, number,
  quantity, foil toggle, printing dropdown, remove row) and a confirm button.
- Mobile: capture screen with a card-shaped framing guide, then the same review screen.
- Tests: fixtures of 20 to 30 real photos (modern, old, foil, sleeved, angled, non-English,
  multi-card) checked in, with the model client mocked in unit tests and a separate
  opt-in accuracy script that runs against the real model and prints a hit rate.

### Stage 2 - Art fingerprint index (2 to 3 weeks, do it when Stage 1 usage justifies it)

Makes the common case - one card, held up to the camera - instant, free, and eventually
offline. Stage 1 stays as the fallback for anything the hash cannot settle and for
multi-card photos.

**Web migration:** `card_image_hash (card_id PK/FK, art_hash bytea, full_hash bytea,
source_image_url text, computed_at timestamptz)`. Roughly 100k rows, ~40 bytes each.

**scry:** new command `hash-images [--all|--missing]`. For each card with a `scryfall_id`
and no current hash, fetch the art crop from the Scryfall CDN (the path tail is already
derivable - `build_scryfall_image_path`, mirrored in web's `scryfall-image.util.ts`), plus
the normal-size image for the full-card hash. Compute a difference hash and a perceptual
hash, write both. Respect Scryfall's rate guidance; the first full pass is a few hours,
after which it is a few hundred cards per new set. Wire it into cron *after* the nightly
ingest, on the same wrapper pattern as the other jobs.

**web:** load the index into memory at boot (100k x 2 x 8 bytes is under 2 MB; refresh on
an interval or on demand). Matching is a linear Hamming-distance scan, which at that size
is well under a millisecond and needs no index structure and no native dependency.
`POST /api/v1/inventory/scan` gains a mode that takes an already-cropped card image,
hashes it the same way, and returns the top N by distance with the distances included so
the UI can say "confident" versus "pick one".

**Client-side detection is the real work here.** The server should receive a
perspective-corrected card image, not a photo of a table. On mobile that is a camera frame
plus edge detection; on web it is a canvas pass. Start with the cheap version: an on-screen
card-shaped guide, and the client crops to that rectangle. Only build real quadrilateral
detection if the guided crop measurably underperforms. If real detection turns out to need
OpenCV on the server after all, that is the one and only trigger to add a sidecar, and it
should be a scry subcommand first.

**Verification:** the same photo fixture set from Stage 1 becomes the regression suite.
The hash path must beat or match Stage 1's hit rate on single-card photos before it becomes
the default, otherwise it stays behind the model.

### Stage 3 - Collector-line reading and on-device matching (optional, later)

- **Collector line OCR** on the warped crop, using the platform's free on-device text
  recognition (Apple Vision, ML Kit on Android). Costs nothing per scan and upgrades an
  ambiguous art match to an exact printing. This is the single highest-value addition once
  Stage 2 exists, because it fixes the reprint-collapse problem for modern cards.
- **On-device index.** Ship the hash index to the app (a couple of MB) so single-card scans
  work with no network and with no per-scan cost at all. This is what makes continuous
  "scan a stack one card after another" feel good, which is the actual killer use case for
  inventorying a collection.
- **Continuous scan mode**: keep the camera open, detect, hash, match, add, haptic
  confirm, next card. This is the feature people will actually talk about. It is only
  reachable once matching is local and instant.

## 4. Ordering and dependencies

```
Stage 0 (decide bar + quota + premium gate)
   |
Stage 1  web: scan endpoint -> CardImportResolver -> review UI -> existing inventory write
   |     mobile: capture + review screen
   |     (ships a working feature; everything after is cost and latency reduction)
   |
Stage 2  web migration: card_image_hash   -->  scry: hash-images command + cron
             |                                        |
             +------------------ both landed ---------+
                                  |
                      web: in-memory match + crop-mode endpoint
                                  |
                      clients: guided crop before upload
   |
Stage 3  on-device OCR of the collector line
         on-device index + continuous scan
```

Cross-repo rule applies at Stage 2: **publish scry first, deploy web second**, and the web
migration that creates `card_image_hash` must be deployed before the new scry binary is
hand-refreshed on the server. Since the deploy runs migrations before extracting the
binary, a single normal web deploy after a scry publish gets the order right on its own.

## 6. Open questions for you

- Is a per-scan cost acceptable at all, or does this have to be free-to-run from day one?
  If it must be free to run, Stage 2 becomes Stage 1 and the timeline roughly doubles
  before anything ships.
- Should scanning be Premium-only from launch, or free with a small monthly quota to
  drive signups (the same argument that moved CSV import to Free in Phase 5.1)?
- Web camera capture, or web upload-only with capture on mobile? Upload-only on web is a
  meaningful simplification and web users are more likely to be at a desk anyway.
